上下文满了先腾地方Context Compact

四步压缩，从最便宜的做起

解决什么问题 · 窗口是硬上限。读过的文件、命令输出、模型回复都堆在 messages 里，迟早撑爆——一撑爆，这一轮就直接失败。作者的做法是四步管线：能外置的先外置，能归档的先归档，都不行了才请模型写摘要。

思路

  1. 第一步 tool_result_budget：只看最新一批工具结果，单个结果太大就落盘，上下文里留路径；
  2. 第二步 snip_compact：消息条数超过 50，就把中间那段整体归档，用一行 [N messages archived] 标记替换；
  3. 第三步 micro_compact：还超过 5 万字符，就把模型已经读过的旧结果截成路径占位，最近 3 条不动；之后还有 fit_tool_results，按结果大小再压一轮；
  4. 第四步 compact_history：仍然超限，才调模型写状态摘要，替换整段历史。

369 if not messages:
370 return messages

372 if messages[-1].get("role") != "user" or not isinstance(content, list):
373 return messages

L519–536

L537–545

一个进程一个压缩器，transcript 和 tool-results 都落在工作区里，事后可以翻。

记住这几条

四步，从便宜到贵

外置（写文件）→ 归档（写 transcript）→ 截断（改字符串）→ 摘要（调模型）。

只有第四步花钱

前三步都是确定性的文件操作，不产生 API 调用，所以可以每轮都跑。

每一步都重量一次

够了就停，不做多余功——这是管线设计里最容易被忽略的一点。

micro 之后还有 fit_tool_results

按结果大小排序，把大的替换成带 1000 字预览的占位；这一步仍然不调模型。

先落盘再替换

任何一步都能按路径恢复，压缩不等于丢失。

别动最新结果

unseen_tool_result_positions 保住的正是模型刚要用的那批。

容易踩的坑

  • 剪消息时切断 tool_use / tool_result 的配对，下一轮 API 直接 400——snip 的边界要往前对齐。
  • 摘要丢掉关键事实（文件路径、报错原文、已做的决定），模型只能重新猜一遍。
  • 把模型还没看到的结果截了，它会以为工具没跑，转头再调一次。

动手改一改

把 CONTEXT_CHAR_LIMIT 改成 5000，让它读一个 300 行的文件再改两处代码，观察四步分别在什么时候触发（看 [auto compact] 和 [transcript saved: ...] 两条输出）。
