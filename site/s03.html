核心节选 · 10 处注解

执行前先过三道闸Permission

权限管线决定哪些操作需要审批

解决什么问题 · 模型会写出 rm -rf /，也会想改工作区外的文件。光在 prompt 里写「不要删库」没用——约束必须写进代码，放在工具真正执行之前。

思路

  1. 第一道：黑名单，命中直接毙掉，连问都不问；
  2. 第二道：规则，危险但可能合理（比如 rm、chmod 777、写到工作区外），拦下来问人；
  3. 第三道：人。回车默认拒绝；
  4. 被拒也要回一条 tool_result，让模型知道「这条路不通」。

记住这几条

顺序：黑名单 → 规则 → 人

越靠前的闸越便宜、越绝对；别把该直接拒绝的事拿去问用户。

默认拒绝

回车等于 No。安全设计里，默认值比提示语更重要。

拒绝也是结果

被拒要回一条 tool_result，模型才能换方案。

约束写在代码里

prompt 里的「请不要」只是建议，代码里的闸门才是约束。

黑名单 ≠ 沙箱

s03 只做命令字符串匹配和一次人工确认；bash 仍可读写工作区外文件、访问网络。真正的边界靠容器/虚拟机/系统权限。

容易踩的坑

  • 只靠 system prompt 约束模型，换个说法它就绕过去了——但 s03 的黑名单也不是安全边界，它只是字符串匹配。
  • 黑名单用简单的 `in` 匹配，`rm -rf`（两个空格）或 `$CMD` 就能绕过——书里是教学简化，真实产品要解析命令。
  • 被拒绝后不给模型任何反馈，它会原地重试，白白烧 token。

动手改一改

给 DENY_LIST 加一条 `"git push --force"`，然后让模型执行它。验收：命令在执行前就被拦下并打印 `Blocked: 'git push --force' is on the deny list`，模型收到的是 Permission denied。不要用「删掉某条保护」来做练习。
