单步交给模型，编排交给脚本Workflow Runtime

demo 离线跑；只有交互 CLI 才装真实 runner

解决什么问题 · 多步流程里，如果每一步都由模型决定下一步，既慢又贵，而且同一份输入跑两次结果可能不同。这一章的 demo 默认用 MockAgentRunner，不联网、不花钱；真实模型只在交互模式里接上。

思路

  1. 编排写成脚本：谁先谁后、串行还是并行、失败怎么重试；
  2. 每一步仍是一次模型调用，但只负责「这一步」；
  3. 带 schema 的输出会校验，失败重试一次；
  4. 每一步追加写 journal；resume 时只有 key 完全相同才复用缓存。

记住这几条

三种入口

`demo` 离线演示、`resume` 离线续跑、无参数进入交互 CLI。

demo/resume 不花钱

默认 RUNNER_FACTORY = MockAgentRunner，返回确定性结果。

真实 runner 由 host 安装

install_workflow_tool(host) 里改成 AnthropicAgentRunner(host.client, host.MODEL)。

不能无参替换

AnthropicAgentRunner 的构造函数需要 client 和 model；直接替换类名会 TypeError。

journal 支持续跑

resume 只读同一次 run 的 journal；新 demo 是新 run；key = kind + label + prompt + schema，四项全同才复用。

费用看请求，不看返回

`client.messages.create` 发出就可能计费；解析失败、重试或抛异常都不会退。

容易踩的坑

  • 以为 `demo` 在调真模型——它用的是 MockAgentRunner。
  • 把 RUNNER_FACTORY 直接赋成 AnthropicAgentRunner：缺少 client/model，直接报错。
  • 以为只有成功返回才计费：请求一发出就可能计费，解析失败也一样。
  • 以为改了 prompt 还能命中缓存：key 含 kind/label/prompt/schema，改了就会重跑。
  • 以为后台任务会主动叫醒模型：只有主循环每轮开头 collect 才注入通知。

动手改一改

步骤：在 `s16_workflow_runtime/` 目录跑 `python code.py demo`，记下输出的 `agents` 数、`tokens` 和 `journal=.runtime/<runId>.journal.jsonl`；再跑 `python code.py resume`。确定性验收：两次退出码为 0；resume 打印 `resuming <runId>`；agents 数小于第一次；tokens 是 Mock 按字符估算的数值，不代表真实计费；journal 文件存在，里面能查到第一次的记录；resume 的进度里会出现 cached。观察项：result 里的具体条目和摘要文字。常见失败：在错误 cwd 运行（找不到 s15）、没有先 demo 就 resume、删了 `.runtime`、无参数进入 CLI（会走真实 runner，可能计费）。
