工具改由外部提供MCP

内存版 mock：清单 + 宿主策略，没有真实传输

解决什么问题 · 每接一个外部服务（文档、部署平台），就要手写工具定义、参数格式、调用代码。接十个就乱成一锅粥。

思路

  1. 服务端声明「我有哪些工具、参数是什么」；
  2. 宿主负责连接、改名、加权限策略，再并进工具池；
  3. 调用统一走 call_tool，异常收成字符串；
  4. 要不要审批由宿主配置决定，不信任服务端的描述。

L170–170

这一章的 MCP 是「内存里的替身」：模拟 tools/list 与 tools/call，没有真实的 stdio/HTTP 连接。

L171–178

注册时先校验：名字非空、不重复、每个工具都有实现。第三方的东西，进门先体检。

L179–190

调用只做一件事：按名找 handler，展开参数，把异常收成字符串。

L191–197

不能把第三方异常直接抛进主循环——那会让整个 agent 崩掉，而不是让模型看到一条错误。

L198–205

最关键的安全设计：某个工具要不要审批，由宿主的策略表决定，而不是读服务端自己写的 description。

记住这几条

这是 mock，不是真实连接

没有 JSON-RPC、没有 stdio/HTTP transport；换成真协议要另写连接层。

工具池是动态的

连上服务才知道有哪些工具，schema 和 handler 一起并入。

宿主掌握策略

服务端的描述是「广告」，不是「授权」；没配置默认 confirm。

错误收成字符串

外部代码失败，对模型来说就是一次普通的工具失败。

命名要归一化

外部工具名可能带奇怪字符，先清洗再加 mcp__server__ 前缀。

容易踩的坑

  • 以为跑通这一章就等于接上了真实 MCP 服务——中间还差一整个传输层。
  • 工具名冲突：归一化后撞名会直接报错，不会静默覆盖。
  • 把服务端的描述当指令直接塞进 prompt，等于让第三方给你下命令。
  • 连接失败就整个启动失败，生产环境应降级成「这个服务不可用」。

动手改一改

照着 _mock_server_docs 再写一个 mock server，只暴露一个工具。验收：工具以 `mcp__<server>__<tool>` 出现在工具池里，且没有在 MCP_HOST_POLICY 配置时调用会要求确认。
